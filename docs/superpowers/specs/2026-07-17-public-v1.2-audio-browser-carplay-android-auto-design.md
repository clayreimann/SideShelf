# Public v1.2 Audio Browser, CarPlay, and Android Auto — Design Spec

**Date:** 2026-07-17
**Status:** Proposed — ready for user review
**Public release:** 1.2
**Primary dependency candidate:** `radio-garden/react-native-audio-browser`

---

## Versioning Context

SideShelf used `v1.0` through `v1.3` for internal engineering milestones before its first public release. Those names remain historical planning identifiers. This document uses **public 1.2**, meaning the second feature release after the initial public 1.0 launch.

---

## Goal

Replace RNTP with Audio Browser as SideShelf's local playback engine and use its browsable media model to ship a safe, useful library experience in CarPlay and Android Auto.

Public 1.2 preserves all public 1.0 and 1.1 phone playback behavior while adding car-native access to Continue Listening, downloaded and recent audiobooks, podcast shows, and podcast Up Next. Users can choose and control content without touching the phone.

This release remains in the Expo managed-development model through source-controlled config plugins/local Expo modules, Expo prebuild, development builds, and EAS. It does not need to work in Expo Go.

---

## Product Decisions

- Audio Browser is the primary replacement candidate for RNTP.
- RNTP remains the public 1.0/1.1 production baseline.
- Public 1.1 podcast behavior is part of the player-migration acceptance contract.
- Car support means a browsable library, not only a Now Playing screen.
- The car hierarchy is intentionally narrower than full mobile-library parity.
- CarPlay and Android Auto control the local phone media session; Google Cast remains deferred.
- SideShelf is willing to contribute missing general-purpose pieces upstream to Audio Browser.
- A permanent private fork is undesirable. Temporary pins or a short-lived fork are acceptable only while upstream contributions are reviewed.
- RNTP and Audio Browser may coexist during development, but the released app should not carry two complete local playback backends indefinitely.

---

## Why Audio Browser

Audio Browser is designed around a browser-like media navigation tree and advertises first-class Android Auto and Apple CarPlay support. Its native implementation uses the platform media frameworks needed for car discovery and browsing, while exposing playback, queue, remote-command, search, favorites, sleep-timer, and output APIs familiar to an RNTP-based application.

It is a stronger architectural match for SideShelf's future than layering independent CarPlay and Android Auto libraries around RNTP.

It is also currently an alpha project. Its repository warns that APIs may change, identifies version `0.1.0`, and still has incomplete Android Auto documentation. Public 1.2 must therefore begin with a compatibility and contribution phase, not with an immediate production dependency swap.

- [Audio Browser Android Auto guide](https://github.com/radio-garden/react-native-audio-browser/blob/main/docs/guide/android-auto.md)

## Release Dependencies

Public 1.2 depends on:

- Public 1.1 podcast media identity, episode progress, Up Next, and downloads being stable.
- Initial public-release feedback confirming the current coordinator and local playback behavior.
- Apple approval for the CarPlay audio entitlement.
- A supported Expo/React Native/Audio Browser/Nitro Modules combination.
- Successful physical-device or representative head-unit qualification on both platforms.

The CarPlay entitlement request should begin early because approval and provisioning are external gates.

## Migration Principles

### Preserve Coordinator Authority

The coordinator remains the single decision-maker. Audio Browser replaces native execution and media-session plumbing; it does not become a second state machine that UI and services call directly.

```text
Routes / UI
    -> coordinator events
        -> PlayerService facade
            -> local playback adapter
                -> Audio Browser native APIs
```

Native Audio Browser events return as factual coordinator events. UI, queue services, downloads, and progress synchronization never call Audio Browser directly.

### Stable Product Identity

Library item IDs, episode IDs, queue-entry IDs, session IDs, and file IDs remain SideShelf/Audiobookshelf concepts. Stream URLs, Audio Browser route URLs, and native queue indexes are transient implementation details.

This is especially important because Audio Browser has an open design concern around opaque track identity. SideShelf must not use a signed URL as its durable media ID.

Related issue:

- [Audio Browser issue 47 — track identity](https://github.com/radio-garden/react-native-audio-browser/issues/47)

### No Permanent Dual-player Architecture

During development, a build-time flag or isolated branch may select RNTP or Audio Browser. That seam exists to compare behavior and provide a development rollback, not to make every release support two native players forever.

Before public 1.2 ships:

- Audio Browser must pass the parity and car gates.
- RNTP production code and dependency should be removed from the public 1.2 build.
- The public 1.1 branch/tag remains the operational rollback baseline.

### Contribute General Fixes Upstream

General-purpose work should be proposed to Audio Browser upstream, including where appropriate:

- Expo config-plugin support.
- Stable opaque media identity.
- Audiobook/podcast progress fields for car displays.
- CarPlay cold-start and browse-loading behavior.
- Android Auto documentation and examples.
- Authenticated request/header configuration.
- Compatibility fixes for the Expo-supported React Native version.

SideShelf-specific Audiobookshelf data mapping remains in SideShelf.

## Phase 0: Compatibility and Upstream Spike

This spike may begin during public 1.1 development, but it must remain isolated from the public 1.1 release.

### Build Questions

- Does Audio Browser build under the Expo SDK and React Native version selected for public 1.2?
- Which `react-native-nitro-modules` version is compatible?
- Does iOS build with SideShelf's Swift, deployment target, New Architecture, and Expo modules?
- Does Android build with SideShelf's Kotlin, Gradle, Media3, New Architecture, and minimum SDK choices?
- Can all native setup be reproduced from a clean prebuild?

### Playback Questions

- Multi-file audiobook streaming and local-file playback.
- Aggregate seeking across files.
- Podcast episode playback using stable `episodeId`.
- Authenticated URLs or headers.
- Playback rate, volume, sleep timer, smart rewind, skip intervals, and output selection.
- Background playback, interruptions, route changes, and app-killed behavior.
- Queue rebuild and process restoration.
- Now Playing metadata, artwork, chapters, and lock-screen controls.

### Car Questions

- Android Auto browse-tree cold start without opening the phone UI.
- CarPlay scene connection and headless React Native startup.
- Browse-node refresh after authentication, sync, or download changes.
- Search/play-from-ID behavior.
- Progress and played-state presentation for audiobooks and podcast episodes.

### Spike Exit Criteria

The production migration is allowed to proceed only when:

1. Clean Expo prebuilds compile on iOS and Android.
2. One streaming and one downloaded audiobook play end-to-end.
3. One streaming and one downloaded podcast episode play end-to-end.
4. Stable logical IDs can be recovered from every native event.
5. Background and app-killed playback are demonstrably viable.
6. A minimal browse tree appears in Android Auto and CarPlay test environments.
7. Blocking upstream gaps have an accepted solution: released upstream, pinned commit, or narrowly scoped temporary patch with an exit plan.

Failure of these gates keeps RNTP as the production player and moves car support out of public 1.2 rather than weakening the release.

## Managed Expo Native Integration

“Managed Expo” for this release means:

- Expo application configuration remains the source of truth.
- Native dependencies are installed through autolinking and config plugins.
- App-specific native integration lives in a local Expo module or source-controlled config plugin.
- `npx expo prebuild --clean` can reproduce required iOS and Android changes.
- Development/EAS builds are used; Expo Go is not supported.
- Generated native files are not the only record of required setup.

### Required iOS Integration

- Request and provision the CarPlay audio entitlement.
- Add the CarPlay scene manifest and Audio Browser scene delegate.
- Connect scene configuration through the Expo-compatible app delegate lifecycle.
- Support headless/background initialization when CarPlay launches the app without the phone UI.
- Preserve audio background mode and existing route/AirPlay behavior.
- Add Siri media intents only if required for approved voice-search scope and supported reliably by the library.

Apple's audio-app model uses CarPlay list templates and the shared Now Playing template, and requires the CarPlay audio entitlement.

Sources:

- [Requesting CarPlay entitlements](https://developer.apple.com/documentation/carplay/requesting-carplay-entitlements)
- [Integrating CarPlay with a music app](https://developer.apple.com/documentation/carplay/integrating-carplay-with-your-music-app)
- [`CPNowPlayingTemplate`](https://developer.apple.com/documentation/carplay/cpnowplayingtemplate)

### Required Android Integration

- Register the Media3 media-library/session service supplied by Audio Browser.
- Add the Android Auto automotive application descriptor and manifest metadata.
- Expose a browsable hierarchy through the media library service.
- Support media-button, voice-search, play-from-ID, and background foreground-service behavior.
- Verify Android Auto projection; Android Automotive OS standalone distribution is out of scope.

Android's media-app guidance requires a media session plus a browser/library service for browseable car content.

Sources:

- [Android media apps for cars overview](https://developer.android.com/training/cars/media)
- [Configure the manifest for media apps](https://developer.android.com/training/cars/media/configure-manifest)
- [Media3 background playback](https://developer.android.com/media/media3/session/background-playback)

## Local Playback Parity

Audio Browser must replace RNTP without regressing:

### Audiobooks

- Multi-file streaming and local playback.
- Continuous aggregate position and seeking.
- Resume reconciliation and smart rewind.
- Chapters and chapter jumps.
- Bookmarks and explicit-seek semantics.
- Mixed local/streaming recovery for partial downloads.
- File-path repair after iOS container changes.

### Podcasts

- Episode identity and episode-specific play sessions.
- Up Next advancement and per-show autoplay.
- Stream and downloaded playback.
- Played state and episode progress.
- App restart with an active episode and persistent queue.

### Shared Player Behavior

- Play, pause, stop, seek, jump forward/back, rate, and volume.
- Sleep timer and final fade.
- Now Playing and lock-screen metadata.
- Audio interruptions, ducking, route changes, Bluetooth, AirPlay/output picker, and headset controls.
- Background playback and app-killed continuation.
- Session start, periodic progress, close, retry, and offline sync.
- Coordinator traces, rejected-transition behavior, and state/store propagation.

The migration plan should create contract tests around this behavior before changing the native implementation.

## Car Browse Information Architecture

### Root

The car root is intentionally concise:

1. **Continue Listening**
2. **Up Next**
3. **Downloaded**
4. **Recent Audiobooks**
5. **Podcasts**

Search is exposed through the platform's supported voice or search entry point rather than as a large on-screen keyboard flow.

### Continue Listening

Contains resumable audiobooks and podcast episodes ordered by recent activity. Entries start at canonical progress and use media-specific title/subtitle/artwork.

### Up Next

Contains the public 1.1 podcast queue. Selecting an entry starts it and preserves the remaining app-owned order. Basic next/previous behavior follows that queue.

### Downloaded

Contains media currently playable without server access:

- Fully downloaded audiobooks.
- Downloaded podcast episodes.

Partial audiobooks appear only if SideShelf can guarantee the selected resume path is locally playable; otherwise they remain phone-only until the user reconnects.

### Recent Audiobooks

Contains a bounded list of recently added or recently accessed audiobooks. Full series and author browsing is deferred to avoid excessive driving-time hierarchy depth.

### Podcasts

Lists podcast shows. A show opens a bounded episode list prioritizing Up Next, in-progress, downloaded, and recent unplayed episodes. Deep history remains available on the phone.

### Browse-node Rules

- Every playable node has stable logical identity.
- Browsable and playable states are explicit.
- Lists are bounded, paginated, or lazily loaded.
- The tree can be built from local database/cache state before network refresh.
- Server-unavailable state never produces an endless loading screen.
- Updates after sync/download changes are invalidated through one browse-data service.
- Artwork has a local/cache fallback safe for headless launch.

## Car Playback and Controls

Public 1.2 must support:

- Start audiobook or episode from the browse tree.
- Resume from canonical progress.
- Play and pause.
- Jump backward and forward using SideShelf settings where the platform allows.
- Seek through platform-provided Now Playing controls.
- Next/previous podcast episode when Up Next applies.
- Accurate title, subtitle, artwork, duration, and progress.
- Playback-rate control where the platform and Audio Browser expose it safely.
- Android Auto voice search/play-from-ID using the platform media-search contract.
- CarPlay Siri media search through `INPlayMediaIntent` when the production entitlement and Audio Browser integration support it; if Apple or the dependency blocks this path, the release must document the limitation and omit the assistant entry rather than expose a broken control.

The car interface does not initiate downloads, edit podcast retention settings, manage bookmarks, reorder Up Next, or expose diagnostic/settings screens. Those remain phone tasks.

---

## Browse Data Architecture

A single platform-neutral browse service feeds both car platforms:

```text
Audiobookshelf sync + local DB + PodcastQueueService + downloads
    -> CarBrowseService
        -> stable BrowseNode tree
            -> Audio Browser routes/content
                -> Android Auto MediaLibraryService
                -> CarPlay list templates
```

`CarBrowseService` owns product selection and ordering. Audio Browser owns native transport of the hierarchy. Platform-specific code must not independently query the database or recreate business rules.

The service must support headless reads, bounded response time, cache-first results, explicit refresh/invalidation, and user/server scoping.

## Error Handling

- Car browse initializes from cached local state when authentication refresh or network access is unavailable.
- Streaming-only items are omitted or marked unavailable when the server cannot be reached; downloaded content remains available.
- A missing local file triggers the existing repair/reconciliation path before failing playback.
- Browse-route load errors return an empty/error state rather than hanging the car UI.
- A failed selection leaves the user in the current browse context and reports a concise platform-safe error.
- Native player errors enter the coordinator's existing error/recovery paths with stable media identity.
- Car scene or media-service startup must not create a duplicate listening session.
- If Audio Browser emits duplicate or out-of-order native events, the adapter normalizes them before coordinator dispatch.

## Testing Strategy

### Contract Tests

Run the same player behavior suite against RNTP before migration and Audio Browser during migration:

- State and command mapping.
- Media identity.
- Position and duration.
- Queue/file transitions.
- Errors and restoration.
- Background events and remote controls.

### Browse Tests

- Root hierarchy and ordering.
- Stable IDs and user/server isolation.
- Cache-first and offline results.
- Pagination/bounds for large libraries and podcast feeds.
- Queue/download/sync invalidation.
- Play-from-ID and search resolution.

### Native Integration Tests

- Clean Expo prebuild and native build for both platforms.
- CarPlay scene/headless initialization.
- Android media service initialization and browse connection.
- Background, app-killed, interruption, Bluetooth, and route behavior.
- No duplicate services, listeners, progress timers, or sessions after reconnect.

### Simulator and Head-unit Tests

- Apple CarPlay Simulator for navigation and template behavior.
- Android Desktop Head Unit for browsing, search, and controls.
- Automated smoke flows where platform tooling permits.

### Physical Qualification

Before release, test:

- At least one physical CarPlay configuration.
- At least one physical Android Auto configuration.
- Streaming and downloaded audiobook playback.
- Streaming and downloaded podcast playback.
- Cold car launch without first opening the phone UI.
- Phone backgrounding, locking, process pressure, disconnect, and reconnect.
- Long-form playback across an audiobook file boundary and podcast queue transition.

Simulator-only validation is insufficient for public 1.2.

## Release Gates

Public 1.2 is ready only when:

1. Audio Browser passes all local playback parity requirements on iOS and Android.
2. Public 1.1 podcast queue, downloads, progress, and autoplay remain correct.
3. A clean Expo prebuild reproduces all native car configuration.
4. Apple has granted the CarPlay audio entitlement for the production identifier.
5. CarPlay and Android Auto can cold-launch, browse cached content, select media, and control playback without opening the phone UI first.
6. Continue Listening, Up Next, Downloaded, Recent Audiobooks, and Podcasts behave consistently across both platforms.
7. Background/app-killed playback, reconnect, and listening-session accounting pass on physical devices.
8. Stable media identity never depends on an expiring URL.
9. Blocking Audio Browser patches have an upstream or documented temporary-pin exit path.
10. RNTP is absent from the public 1.2 production dependency graph, while the public 1.1 tag remains a rollback baseline.

## Suggested Delivery Slices

The future implementation plan should decompose public 1.2 approximately as follows:

1. Compatibility spike, entitlement request, and upstream issue/PR plan.
2. Player contract tests and platform-neutral media/timeline boundaries.
3. Audio Browser adapter with audiobook parity.
4. Podcast parity, Up Next, downloads, and background lifecycle.
5. Managed Expo config plugin/local module and clean-prebuild verification.
6. Shared car browse service and Android Auto integration.
7. CarPlay integration and headless startup.
8. RNTP removal, physical qualification, store/distribution checks, and rollback documentation.

Each slice requires explicit go/no-go evidence. A failed dependency or platform gate may defer public 1.2 rather than shipping a partially migrated player.

## Out of Scope

- Google Cast; see [`docs/investigation/google-cast-support.md`](../../investigation/google-cast-support.md).
- Android Automotive OS standalone app distribution.
- Full mobile-library parity in the car.
- Series/author/tag browsing in the initial car hierarchy.
- Adding podcast subscriptions or external discovery.
- Download initiation, retention settings, bookmark editing, or Up Next reordering from the car.
- Custom visual car interfaces outside Apple and Android supported media templates.
- A permanent RNTP/Audio Browser runtime switch in production.
- Carrying a permanent private Audio Browser fork without a separate decision.

---

## Fallback Decision

If Audio Browser cannot meet the build, identity, playback, or headless-car gates within a bounded migration effort:

1. Keep RNTP as the production player.
2. Preserve public 1.1 podcast functionality.
3. Publish the spike findings and upstream blockers.
4. Defer public 1.2 car support or reconsider a narrower native integration in a new design process.

The release number is not a reason to accept a weaker playback foundation. Public 1.2 exists to ship a reliable replacement and car experience together; if the foundation is not ready, the feature waits.
